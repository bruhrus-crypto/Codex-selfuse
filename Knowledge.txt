VM vs runtime vs API (practical boundary)
- Luau VM (language + standard libs): what you see in luau-lang/luau VM sources (base/string/
  table/math/etc). This is the language implementation and default libraries.
- Roblox runtime (sandbox): Roblox hosts the VM and decides which globals/libs are exposed or
  modified (e.g., limited os/debug, no filesystem, task scheduler, security restrictions).
- Roblox API (platform objects): services, instances, events, remotes, and engine types that
  exist outside the VM and are provided by the Roblox engine.
Examples of boundary impact:
- VM provides string/table/math; runtime decides whether os/debug exist; API provides
  game:GetService, Instance, Players, RunService, TweenService, etc.
- Type annotations can cover Luau language types, but Roblox API types (Instance, Vector3,
  CFrame, RBXScriptSignal) are provided by Roblox type definitions, not the VM.
- Code portability: VM-level code can run in standalone Luau; runtime/API code requires Roblox.

Part 1: Basics of Luau (Roblox)
Keywords
- local — creates a local variable scoped to the current block.
- global — (rare in Roblox) creates a global variable; typically avoided in ModuleScripts.
- function — declares a function.
- return — returns a value from a function.
- if / then / elseif / else / end — conditional blocks.
- for / in / do / end — numeric or table iteration (e.g., for i = 1, 10 or for k, v in pairs(tbl)).
- while / do / end — loop with condition checked first.
- repeat / until — loop with condition checked last (runs at least once).
- break — exits the nearest loop.
- continue — not built-in; can be simulated via goto.
- local function — defines a local function within scope.
- do / end — creates a local scope block.
- true / false — boolean values.
- nil — absence of a value.
- and / or / not — logical operators.
- in — used in for ... in iteration.

Basic Luau globals
- print(...) — outputs values to the Output window.
- warn(...) — outputs a warning (yellow) to Output.
- error(msg) — raises an error and stops execution.
- assert(condition, message?) — checks a condition and errors if false.
- typeof(value) — returns Roblox-aware type (e.g., Player, Model, Vector3).
- type(value) — returns Lua type (number, string, table, function, boolean, nil).
- tostring(value) — converts a value to string.
- tonumber(value) — converts a string to number if possible.
- pairs(tbl) — iterates key/value pairs in a table.
- ipairs(tbl) — iterates numeric indices in a table.
- next(tbl, index?) — low-level table iterator.
- select(index, ...) — returns the n-th argument.
- pcall(func, ...) — protected call; returns ok, result/error.
- xpcall(func, errHandler, ...) — protected call with error handler.
- rawget(tbl, key) — read without metatable.
- rawset(tbl, key, value) — write without metatable.
- rawlen(tbl) — length without metatable.
- require(module) — loads a ModuleScript.

Part 15: Ошибки, корректировки и практические стандарты Roblox Luau (без кода)
Что было сделано правильно
- Троттлинг отправки input, safeCall/pcall для клиентских визуалов, whitelist actions/effect types,
  хранение cooldown по userId, и rate-limit логирования отклонений — это правильные паттерны
  надежности и античита.
- Возврат пустой таблицы в type-only ModuleSpecs — практичный runtime-safe подход.

Критичная поправка по времени
- Нельзя напрямую сравнивать клиентский tick() и серверный workspace:GetServerTimeNow() как одну шкалу
  времени без синхронизации offset.
- Безопасная практика: authoritative проверки cooldown/античита вести только по серверному времени,
  клиентский timestamp использовать как вспомогательный сигнал для prediction/reconciliation.

Input/prediction
- Отправка input должна быть с троттлингом (обычно 20-30 Hz) и по возможности только при изменении
  состояния, чтобы снижать сетевой трафик.
- RenderStepped/Heartbeat подходят для отправки при таймере; выбор зависит от задачи, но без спама.
- turretYaw нужно считать от реальной целевой точки (например, mouse.Hit.Position относительно башни),
  а camera lookVector оставлять только как временный placeholder.

Память и cleanup
- Долгоживущие таблицы лучше индексировать по userId, а не Player/Model instance.
- Обязательная очистка в PlayerRemoving/Shutdown/CharacterRemoving и Disconnect() для всех соединений.
- Для треков/визуалов, привязанных к моделям, нужен cleanup при Destroyed/AncestryChanged.

Сеть и релевантность
- FireAllClients применять только когда действительно нужно; иначе отправлять адресно
  (FireClient) или с proximity filtering.
- Payload должен быть минимальным, типизированным и проходить runtime-валидацию на сервере.

Roblox Luau vs open-source Luau (практический срез)
- Roblox Luau = язык Luau + sandbox runtime + Roblox engine API.
- Roblox-специфика: Services, Instance-модель, RBXScriptSignal, Remotes, task API,
  Vector3/CFrame/Color3/UDim2/Enum, RunService loop.
- В sandbox обычно ограничены/отсутствуют низкоуровневые и опасные API (файловая система,
  часть debug/os, некоторые legacy функции).

Жесткие правила для боевой игры
- Никогда не применять урон по клиентскому payload без server-side проверок
  (distance, cooldown, whitelist weapon/projectile, sanity ranges).
- Сервер авторитетен по урону, экономике, сохранению и итоговым позициям.
- Клиентский timestamp не источник истины; при необходимости time-sync делается отдельным handshake.
- Логи отклонений должны быть пороговыми (rate-limited), чтобы не захламлять продакшн-логи.

Типизация и архитектура
- Описывать все сетевые payload через export type в shared-слое и поддерживать runtime-валидацию.
- Модули делать single-responsibility: StateManager, CombatSystem, ProjectileSystem, TankController,
  TankInput, TankPrediction, TankVisuals.
- Для hot-reload/жизненного цикла использовать конвенцию Init/Shutdown с явным cleanup.

Производительность
- Кешировать сервисы/часто используемые ссылки.
- Избегать аллокаций в горячих циклах; использовать pooling для projectiles/VFX/UI.
- Для массовых битв снижать трафик за счет троттлинга input, delta-передачи и релевантных рассылок.

Part 16: Частые ошибки и антипаттерны Roblox Luau + практичные исправления
Remote/сеть
- Сервер не должен вызывать FireServer; это клиентский метод. Сервер отправляет через FireClient/FireAllClients.
- Нельзя доверять клиентским payload без проверки типов, диапазонов, distance/cooldown и whitelist (weaponId/projectileType/action).
- Не слать события каждый кадр без троттлинга; лучше 20-60 Hz и/или send-on-change.
- FireAllClients использовать только для действительно глобальных событий; для большинства эффектов нужна релевантная рассылка (nearby/proximity).
- RemoteFunction не применять для долгих/частых операций; он синхронный и легко блокирует поток.

Время/цикл
- RenderStepped только для клиента и визуала; серверная логика должна идти через Heartbeat/Stepped.
- Клиентский tick и серверный GetServerTimeNow — разные опоры; сравнивать напрямую без time-sync нельзя.
- Authoritative таймеры и cooldown делать только по серверному времени.

Память/жизненный цикл
- Все RBXScriptConnection хранить и отключать в Shutdown/PlayerRemoving/CharacterRemoving.
- Долгоживущие таблицы лучше индексировать по userId; ключи-Instance требуют обязательного cleanup.
- Частое Create/Destroy для VFX/пуль — тяжелый антипаттерн; использовать object pooling.

Физика/античит
- Не принимать хиты/позиции как истину от клиента; сервер верифицирует raycast/дистанцию/временные окна.
- Network ownership нужен для плавности транспорта, но не отменяет server-side проверки.
- Логи отклонений должны быть пороговыми (rate-limited), иначе прод-логи захламляются.

Практичные паттерны оптимизации
- Троттлинг + батчинг сетевых обновлений.
- Interest management: рассылка событий только релевантным игрокам.
- Кеширование сервисов/ссылок и снижение аллокаций в hot-loops.
- Разделение тяжелых задач на кадры (task.defer/task.spawn с лимитами по кадру).
- Профилирование через Studio инструменты (CPU/Memory/Network/MicroProfiler).

Appendix A: Time synchronization (recommended)
- Server периодически отправляет метку времени клиенту (TimeSync -> serverNow).
- Client хранит offset = serverNow - tick().
- При необходимости client отправляет clientTick, сервер оценивает approximateClientTime = clientTick + offset.
- Предпочтительная альтернатива: критические cooldown/checks держать только на сервере и не отклонять
  действия только из-за client timestamp.

Appendix B: Validation helper pattern (concept)
- Helper isNumberInRange(v, min, max): проверяет тип number и диапазон.
- validateAttackPayload(p): проверяет table, damage range, weaponId string, targetUserId number.
- Любой payload проходит schema validation до применения игрового эффекта/урона.

Appendix C: Pooling skeleton (concept)
- Предсоздать N объектов и хранить в пуле.
- Spawn: взять из пула, активировать, переинициализировать transform/state.
- Return: деактивировать, очистить transient state, вернуть обратно в пул.
- Если пул пуст, допускается fallback-аллоцирование с последующим возвратом в пул.

Appendix D: Code-review checklist (быстрый)
- Validate payload schema/type/range.
- Whitelist actions/weapon/projectile ids.
- Server-authoritative damage/economy/state.
- userId keys for long-lived tables.
- Cleanup on PlayerRemoving/CharacterRemoving + Disconnect all connections.
- Input throttling and send-on-change.
- Prefer FireClient/proximity over global FireAllClients.
- Avoid blocking RemoteFunction flows.
- Pool VFX/projectiles/UI objects.
- Use profiler + network stats before release.
- Keep no file/io/system assumptions in Roblox runtime.
- Test validate* functions and critical combat paths.

Part 20: Что нового извлечено из присланных серверных скриптов (TankTurrets_and_Fire / Tank Controller)
Практические наблюдения
- Большие боевые серверные системы часто строятся через _G-шину между модулями
  (_G.activeTanks, _G.tankHealthData, _G.TankMainFire), что ускоряет интеграцию, но требует
  строгой дисциплины инициализации и нейминга.
- Диагностический лог в Workspace через StringValue полезен для live-debug в Studio/QA,
  когда нужно видеть события без просмотра Output.
- Для турелей применим гибридный подход наведения: Motor6D (предпочтительно) с fallback
  на прямой CFrame-поворот при отсутствии корректных joints.
- В сложных танковых ригах важно резолвить части через path-lookup (например Body.Head.Barrel)
  и иметь fallback к PrimaryPart/first BasePart.
- Система фракций может быть вынесена в отдельный модуль (GameStats) с fallback-таблицей,
  чтобы AI/auto-target работали даже при частичной деградации зависимостей.

Надежность и риски (из кода)
- pcall активно используется вокруг чувствительных мест (require, physics fields, damage hooks),
  что снижает вероятность hard-crash в бою.
- В коде встречается дублирование имени RS (повторный local RS), что повышает риск путаницы.
- Использование tick() как универсального времени в серверных скриптах допустимо для internal-cooldowns,
  но для единой шкалы лучше стандартизировать один источник времени внутри модуля.
- Поиск Motor6D через глубокий GetDescendants()/workspace fallback надежен, но потенциально дорог:
  лучше кешировать найденные связи для hot-path наведения.
- Touched-based hit detection в projectile fallback рабочая, но для anti-cheat/стабильности под нагрузкой
  серверный raycast обычно предсказуемее.

Архитектурные паттерны, которые стоит сохранять
- Разделение обязанностей: контроллер движения/режимов и отдельный модуль турелей/огня.
- Явные cooldown/state таблицы per turret (data._turretState[id]) для независимого fire-control.
- Overturn logic c mode switching (MOVE/OVERTURN), sustain-time и angular-velocity checks —
  хороший шаблон для тяжелой техники.
- Export API в глобал для совместимости (например _G.TankMainFire) должен сопровождаться
  контрактом и версионностью, чтобы избежать неявных ломаний при рефакторинге.

Что улучшать в будущем
- Централизовать валидацию payload/дистанций/скоростей в helper-слое.
- Добавить кеширование часто вычисляемых ссылок (motors, barrel parts, turret nodes).
- Перевести критичные hit-пайплайны на серверный raycast + единый damage pipeline.
- Вынести debug logging в переключаемый уровень (dev/staging/prod), чтобы не раздувать runtime-лог.

Part 21: Production Roblox Luau — observability, scaling, networking, team workflow
Production observability
- DataStore не использовать как лог/метрики pipeline: это хранилище прогресса с лимитами и throttling.
- Собирать агрегаты, а не поток сырых событий.
- Три уровня telemetry:
  - client metrics: FPS/input-latency/UI errors (редкая отправка, например 30-60 сек или по событию);
  - server metrics: heartbeat time, active objects, projectile count, memory pressure, remote rate;
  - gameplay metrics: интервальные агрегаты (shots per window, total damage), не каждое действие.
- Для буферизации/доставки telemetry использовать MemoryStoreService или внешний backend через HttpService;
  AnalyticsService — для high-level статистики, не для realtime deep-debug.

Scaling patterns
- Roblox масштабирует серверы горизонтально, но производительность внутри инстанса определяется архитектурой.
- Базовые принципы: server-authoritative state, interest management, spatial partitioning/sector routing.
- Heavy systems масштабировать через pooling, пониженную частоту обновления дальних сущностей и,
  где уместно, через Actor/Parallel Luau.

Networking limits and protocol hygiene
- Практически безопасный диапазон частоты RemoteEvent: примерно 20-30 msg/sec на игрока;
  устойчивость заметно падает при 60+ и особенно 100+.
- Payload держать компактным (обычно <1KB), избегать больших таблиц/длинных строк/лишних полей.
- Вместо отправки позиции каждый кадр — отправка input, velocity hints и периодические authoritative corrections.
- Использовать компактные схемы: numeric IDs вместо длинных строк, округление векторов, минимальный контракт.

Team standards and release process
- Строить код вокруг систем (CombatSystem/ProjectileSystem/DamageSystem), не around single scripts.
- Shared contracts/types в ReplicatedStorage, server systems в ServerScriptService, client controllers в StarterPlayerScripts.
- Модульный lifecycle контракт: Init/Start/Shutdown.
- Для релизов: feature flags, canary rollout, and rollback через параллельные версии (например V1/V2).
- Инженерный процесс: Git + code review + reproducible project structure (например Rojo-based flow).

Ключевой production фокус
- Оптимизируется поток данных: меньше сетевых сообщений, меньше аллокаций Instance,
  меньше дорогой физики на кадр, больше агрегации и предсказания на клиенте с серверной сверкой.
- Следующий углублённый шаг: client prediction + server reconciliation для плавного управления техникой.

Part 22: Пользовательские production-практики и игровые правила (входные требования)
Release/process
- Feature flags используются как основной механизм rollout/rollback без деплоя новой версии.
- Типичный паттерн: переключение между legacy и V2 реализацией через флаг в коде.

Production метрики
- Наиболее полезны gameplay/engine агрегаты: число созданных объектов, частота RemoteEvent,
  активная физика, нагрузка Heartbeat loop.
- Практика: считать агрегаты за интервал (например 10 секунд), а не логировать каждое событие.

Профилирование перед релизом
- Проверять Heartbeat-пути на отсутствие Instance.new/Destroy в кадр.
- Подтверждать, что в hot-loop остаются только вычисления/обновления состояния.

Архитектура модулей
- Предпочтение схеме "тонкий контроллер + чистые модули логики".
- Логические модули работают с данными и минимально зависят от Players/RemoteEvents.

Игровая модель (из текущих требований)
- Урон покомпонентный: у каждой детали MaxHealth/CurrentHealth/Armor.
- Повреждение применяется к конкретной hit-части, что поддерживает disable отдельных подсистем
  (например гусеницы/башня).
- Баланс аркадный с физическими ограничениями (например запрет движения при критичном наклоне).

Server-authoritative правила
- Сервер авторитетен по движению, урону, стрельбе и топливу.
- Клиент отправляет только input-намерения (throttle/steer), без прямой передачи позиции.
- Клиенту оставляется prediction для камеры/UI, но финальное решение принимает сервер.

Античит-приоритеты
- Критичные угрозы: подмена урона, спам RemoteEvent, попытки клиентского контроля позиции.
- Базовое правило: клиент сообщает намерение, сервер вычисляет результат и применяет state changes.

Part 23: Production standards deep-dive (from latest guidance)
Критические практики
- Клиентский tick/os.clock нельзя напрямую сравнивать с server GetServerTimeNow без time-sync offset.
- Authoritative timers/cooldowns должны жить на сервере; клиентский timestamp — только hint для prediction/reconciliation.
- Сервер никогда не принимает готовые позиции/урон/взрывы от клиента, только intent-параметры.
- RemoteFunction (особенно InvokeClient) не использовать в hot-path: блокирует поток и повышает DoS-риск.

Структура проекта и контракт
- Рекомендуемая иерархия: ReplicatedStorage(Shared/Remotes/Prefabs), ServerScriptService(Systems/Services),
  ServerStorage(heavy private templates), StarterPlayerScripts(client controllers), StarterGui(HUD templates).
- Контракт модулей: Init(config), Start(), Shutdown(); минимальные side-effects при require.
- Долгоживущие состояния индексировать по userId; cleanup обязателен в PlayerRemoving/CharacterRemoving.

Сеть, валидация, cooldowns
- OnServerEvent: первый аргумент player; action whitelist + schema validation для каждого payload.
- Для атак: validate damage range, targetUserId, weaponId, timestamp type; потом server-side checks (distance/LOS/cooldown).
- Cooldown pattern: cooldownRemaining[userId] обновляется на Heartbeat с dt-accumulator.

Time sync handshake
- Server периодически отправляет serverNow клиенту.
- Client вычисляет offset = serverNow - tick().
- Payload может включать clientTick; сервер использует как вспомогательную оценку времени, не как security source.

Pooling и projectile pipeline
- Пулы обязательны для projectiles/VFX/UI: Acquire/Release + reset transient state.
- Надежный pipeline: validate fire -> spawn/step projectile -> server raycast/hit verify -> unified damage ->
  proximity VFX broadcast.
- Touched можно оставить fallback, но canonical hit truth лучше держать на server raycast.

Telemetry/observability
- DataStore не использовать как telemetry transport.
- Собирать агрегаты по окнам (shots/hits/damage/remote-rate/heartbeat load) и отправлять батчами
  через MemoryStore/HttpService.

Release and anti-cheat operations
- Feature flags + canary + fast rollback (V1/V2) как базовая release-стратегия.
- Anti-cheat baseline: rate limits per action, sanity bounds, ownership checks, distance/LOS checks,
  suspicious-event counters и progressive penalties.

Code review расширенный checklist
- Schema validation + whitelist actions.
- Server-authoritative state transitions only.
- userId keys for long-lived state.
- No Instance.new/Destroy in hot loops; pooling in repeated paths.
- Proximity routing over blanket FireAllClients.
- RemoteFunction kept out of frequent/slow flows.
- Cleanup all connections/tables in lifecycle hooks.
- DataStore uses UpdateAsync + backoff + autosave strategy.
- Profiling passed for CPU/physics/network at high-load scenarios.

Roadmap внедрения
- 1) Unified validation helpers.
- 2) userId-key migration + cleanup hooks.
- 3) pooling rollout.
- 4) server-raycast-first hit pipeline.
- 5) centralized telemetry.
- 6) feature-flag canary + smoke/perf preflight.

Part 24: Mega demo review corrections (critical learnings)
- Client bug: RBXScriptSignal has no :Once(); Tween.Completed must use :Connect() + manual disconnect (or :Wait()).
- Time-source safety: never hard-compare client tick()/os.clock() with workspace:GetServerTimeNow(); keep authoritative cooldown/validation on server time.
- If time sync is needed, store per-user offset from handshake and treat clientTick as prediction hint only.
- VFX should be pooled client-side too; avoid Instance.new per hit burst.
- Prefer Heartbeat/task loop for network send cadence; keep RenderStepped for rendering-sensitive tasks.
- Remove no-op allocations (example: Debris:AddItem(Instance.new("Folder"),0)).
- Server pools should live in dedicated containers (ServerStorage/hidden pool folder), not leave inactive artifacts in Workspace.
- For high-rate proximity checks, use squared-distance compare and evolve to sector/spatial indexing.
- Add finite guards for numeric vectors from client payloads (NaN/Inf defense).
- Whitelist action names before expensive logic; unknown actions handled separately (and optionally separately metered).
- Reject counters should use a time window/sliding buckets, not unbounded lifetime increments.
